# Codex Improvement and Cost Report

Last updated: 2026-05-27
Project: Epub Binder v4.3.4

이 문서는 Codex가 현재 Epub Binder 프로젝트를 더 개선하는 데 쓸 수 있는 기능과,
Vercel, GitHub, Supabase를 붙였을 때 유료 플랜이나 사용량 제한을 부를 수 있는 요소를 따로 정리한 보고서다.

## 1. 현재 결론

- 이 프로젝트는 로컬 Windows PyQt 앱이므로 Vercel과 Supabase는 현재 필요 없다.
- GitHub는 소스 백업과 버전 관리에는 매우 유용하지만, exe와 대용량 테스트 파일을 올리면 저장소가 무거워진다.
- Codex 관점에서 가장 효과 큰 개선은 "프로젝트 지도 유지", "테스트 fixture화", "`main_window.py` 분리", "실제 실행 경로와 테스트 경로 통합"이다.
- 클라우드 서비스를 붙이는 기능은 지금 단계에서는 이득보다 비용/복잡도 리스크가 더 크다.

## 2. Codex 기능별 활용 검토

### 2.1 코드 구조 분석과 프로젝트 지도

활용 가치: 높음

현재 이미 `docs/CODEX_PROJECT_MAP.md`를 만들었다.
다음 작업부터는 전체 폴더를 훑기보다 해당 문서를 먼저 읽고, 기능별 진입점만 좁혀서 보면 된다.

효과:

- 토큰 소모 감소
- `main_window.py` 전체를 반복해서 읽는 문제 완화
- 새 작업자가 들어와도 병합/이름변경/txt2epub/중복정리 위치를 빠르게 파악

추가 개선:

- 큰 기능을 바꿀 때마다 프로젝트 맵 갱신
- `main_window.py` 내부 함수 위치가 크게 변하면 지도 갱신
- 실패 케이스가 새로 생기면 관련 테스트 위치를 지도에 추가

### 2.2 코드 수정과 리팩터링

활용 가치: 매우 높음

현재 가장 큰 개선 후보는 `epub_binder_app/ui/main_window.py` 분리다.
이 파일이 너무 커서 작업할 때마다 위험이 크다.

추천 순서:

1. 기능 변화 없이 탭별 UI를 파일로 분리
2. 실제 앱에서 쓰는 `MergeWorker`와 `epub_binder_app/workers.py`의 중복 제거
3. 이름 변경, txt2epub, 중복 정리의 core 호출 경로 정리
4. 공용 판단 로직은 `epub_binder_core/`로 이동

주의:

- 기능 변경 없는 리팩터링과 기능 수정을 섞지 않는 것이 안전하다.
- 분리할 때마다 관련 테스트를 먼저 돌린다.

### 2.3 테스트 작성과 회귀 방지

활용 가치: 매우 높음

사용자가 실제 TXT/EPUB 케이스를 계속 가져오기 때문에, Codex가 제일 잘 도울 수 있는 부분이다.

추천:

- 실제 실패 파일 전체를 테스트에 넣기보다 문제 패턴만 줄인 fixture를 만든다.
- 통과한 케이스 목록과 실패한 케이스 목록을 문서로 유지한다.
- 목차 감지, 제목 정리, 중복 정리처럼 오탐 위험이 큰 영역은 작은 단위 테스트를 추가한다.

현재 좋은 흐름:

- `pytest` 전체 206개 통과 상태까지 올라왔다.
- txt2epub, 병합 목차, 중복 정리에 회귀 테스트가 많이 생겼다.

추가하면 좋은 테스트:

- 중복 정리에서 시즌/권/부/외전이 다르면 남기는 케이스
- 제목은 비슷하지만 해시가 다른 케이스
- 제목도 같고 해시도 같은 완전 중복 케이스
- 네이버 시리즈 HTML 구조 변경에 대비한 fixture parser 테스트

### 2.4 빌드 자동화

활용 가치: 중간

Codex가 빌드 스크립트 실행, exe 확인, 산출물 정리를 도울 수 있다.
다만 PyInstaller 빌드는 로컬에서 돌리는 것이 가장 안전하다.

추천:

- 로컬 빌드 유지
- 빌드 후 `dist/EpubBinder4.3.4.exe`와 루트 exe의 크기/시간 확인
- `build/`, `dist/`, 루트 exe 정리 규칙 문서화

비추천:

- GitHub Actions에서 매번 PyInstaller exe 빌드
- Vercel/Supabase 같은 웹 서비스에서 변환 작업 실행

### 2.5 UI 검토와 스크린샷 기반 점검

활용 가치: 중간

현재 앱은 PyQt 데스크톱 앱이라 웹 브라우저 자동화보다 직접 exe 테스트가 더 중요하다.
그래도 Codex가 스크린샷을 보고 UI 문제를 정리하거나, 컬럼/색상/간격 개선안을 낼 수 있다.

적합한 작업:

- 중복 정리 탭 시인성 개선
- 작은 창에서 버튼/컬럼 간격 문제 분석
- 챕터 미리보기 표의 색상/상태 표시 개선

### 2.6 GitHub 연동

활용 가치: 높음, 단 초기 설정 후

GitHub는 이 프로젝트에 가장 현실적으로 유용한 외부 서비스다.

좋은 사용법:

- 소스 백업
- 변경 이력 관리
- 태그로 버전 관리
- 작은 fixture와 테스트 관리
- GitHub Issues에 실패 케이스 기록

주의:

- exe, build, dist, 대용량 테스트 원본은 커밋하지 않는다.
- GitHub Actions는 처음에는 `pytest`와 `compileall`만 돌린다.
- PyInstaller 빌드는 로컬 수동 빌드를 기본으로 한다.

### 2.7 자동화/알림

활용 가치: 낮음~중간

정기적으로 돌릴 필요가 있는 서버 앱이 아니므로 자동화는 많이 필요하지 않다.

쓸 만한 경우:

- "다음에 이 폴더의 실패 케이스 정리해줘" 같은 작업 알림
- 릴리즈 전 점검 체크리스트 자동 실행

지금은 필수 아님.

### 2.8 웹 배포/DB/클라우드화

활용 가치: 낮음

현재 앱 성격상 로컬 파일을 직접 만지는 데스크톱 도구가 맞다.
웹 앱으로 바꾸면 파일 업로드, 저장공간, 개인정보, 저작권, 대용량 처리 문제가 생긴다.

권장:

- 클라우드화하지 않는다.
- 로컬 앱 + GitHub 소스 백업 정도가 적절하다.

## 3. Vercel 비용/부하 리스크

현재 사용 여부: 사용 안 함

Vercel을 쓰게 만들 수 있는 기능:

- 웹판 Epub Binder를 배포
- EPUB/TXT 파일 업로드 후 서버에서 변환
- 표지 이미지 미리보기/최적화
- 브라우저에서 중복 정리 결과를 보여주는 대시보드
- 온라인 데모 페이지 제공

유료 플랜 또는 제한 리스크:

- 대용량 EPUB/TXT 업로드로 bandwidth 증가
- 변환 작업을 Serverless Function에서 처리하면 실행 시간/메모리 제한에 걸림
- 이미지 최적화 요청이 많으면 사용량 증가
- exe나 테스트 파일을 정적 파일로 배포하면 트래픽 증가
- 자동 테스트가 배포 URL을 반복 호출하면 불필요한 요청 증가

판단:

- 현재 프로젝트에는 Vercel을 붙이지 않는 것이 좋다.
- 문서 사이트가 꼭 필요하면 정적 문서만 올리고, 파일 변환/다운로드는 절대 맡기지 않는다.

## 4. GitHub 비용/부하 리스크

현재 사용 여부: 아직 git 저장소 아님

GitHub를 쓰게 만들 수 있는 기능:

- 소스 저장소 생성
- 버전 태그 관리
- GitHub Releases에 exe 업로드
- GitHub Actions로 테스트 자동화
- Issues에 실패 케이스 관리
- Pull Request로 변경 검토

유료 플랜 또는 제한 리스크:

- private repository에서 Actions 사용량이 많으면 무료 한도를 소모
- PyInstaller 빌드를 Actions에서 자주 돌리면 minutes를 많이 씀
- exe, dist, build, 대형 EPUB/TXT를 커밋하면 저장소 용량이 커짐
- Git LFS를 쓰면 LFS 저장공간/트래픽 제한에 걸릴 수 있음
- Actions artifact를 계속 보관하면 저장공간이 쌓임
- release asset으로 exe를 자주 올리면 관리 부담이 커짐

권장 `.gitignore` 원칙:

```gitignore
.venv/
build/
dist/
__pycache__/
.pytest_cache/
*.exe
*.spec
*.log
테스트/
중복정리/
보관_*/
```

단, `*.spec`은 빌드 재현성이 필요하면 추적해도 된다.
현재 프로젝트에서는 spec이 버전별로 생성되는 산출물 성격도 있어서 처음에는 제외가 안전하다.

추천 GitHub 사용 방식:

1. 첫 커밋은 소스와 작은 테스트만 포함
2. 큰 테스트 원본은 로컬 보관
3. CI는 `pytest -q`와 `compileall`만 실행
4. exe 빌드는 로컬에서 하고, 안정본만 수동 Release 업로드

판단:

- GitHub는 쓰는 것이 좋다.
- 다만 "소스 저장소"로만 쓰고, 대용량 파일 창고나 빌드 서버처럼 쓰면 비용/관리 리스크가 커진다.

## 5. Supabase 비용/부하 리스크

현재 사용 여부: 사용 안 함

Supabase를 쓰게 만들 수 있는 기능:

- 변환 기록 DB 저장
- 사용자별 작업 목록 저장
- EPUB/TXT/표지 파일 Storage 저장
- 여러 PC 간 설정 동기화
- Realtime으로 작업 진행률 공유
- Edge Functions에서 변환/해시 계산 실행

유료 플랜 또는 제한 리스크:

- Storage에 EPUB/TXT/표지 저장 시 용량 증가
- 대용량 다운로드/공유로 egress 증가
- DB에 파일 메타/로그를 계속 쌓으면 저장공간 증가
- Realtime 구독을 켜면 접속 수/메시지 사용량 증가
- Edge Functions에서 변환/해시/압축을 돌리면 실행량 증가
- 인증/사용자 관리가 들어가면 운영 복잡도 증가

판단:

- 현재 프로젝트에는 Supabase가 필요 없다.
- 로컬 설정 파일과 로컬 작업 기록이면 충분하다.
- 동기화가 정말 필요해져도 먼저 GitHub 백업이나 수동 백업으로 해결하는 편이 낫다.

## 6. 비용을 부르는 기능 목록

아래 기능들은 편해 보이지만 유료 플랜이나 사용량 초과를 부를 수 있다.

| 기능 | 위험 서비스 | 이유 | 권장 |
|---|---|---|---|
| 웹에서 EPUB 변환 | Vercel, Supabase | 대용량 업로드/실행 시간/저장공간 | 하지 않음 |
| 표지 이미지 대량 캐시 | Vercel, Supabase | 이미지 트래픽/Storage 증가 | 로컬 캐시만 |
| exe 자동 빌드 CI | GitHub | Actions minutes 큼 | 로컬 빌드 |
| exe를 매번 Release 업로드 | GitHub | 관리/용량 부담 | 안정본만 수동 |
| 테스트 원본 EPUB/TXT 커밋 | GitHub | 저장소 비대화 | 작은 fixture만 |
| 작업 로그 클라우드 저장 | Supabase | DB/Storage 누적 | 로컬 로그 |
| 실시간 진행률 공유 | Supabase | Realtime 사용량 | 불필요 |
| 웹 대시보드 | Vercel, Supabase | 배포/DB/트래픽 관리 필요 | 현재 불필요 |

## 7. 추천 운영 방향

### 지금 가장 좋은 조합

- 로컬 PyQt 앱 유지
- GitHub는 소스 백업과 버전 관리 용도로만 사용
- Vercel 사용 안 함
- Supabase 사용 안 함
- 큰 샘플과 exe는 로컬 보관
- 실패 케이스는 작은 fixture로 축소해서 테스트에 반영

### Codex 작업 방식

1. `docs/CODEX_PROJECT_MAP.md`로 위치 파악
2. 관련 core 파일과 테스트만 읽기
3. 작은 단위로 수정
4. `pytest` 또는 관련 테스트 실행
5. 필요할 때만 빌드
6. 변경 후 이 보고서나 프로젝트 맵 갱신
